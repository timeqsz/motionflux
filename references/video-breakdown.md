# 拆解视频里的动效

目标是说明「什么在动、怎样动、为何在这里动、如何复现」，而非列效果名或复述视频内容。沿用用户指定范围；没指定时先通看，按镜头和关键动作整理，重复动作可合并并注明时间段。

拆解的交付物是**拆解表 ＋ 拆解动图**：动图上半部分是**截取的原片片段**，下半部分按动效类型分轨，同一轨道容纳多个独立动作块，各块在自己的作用时段亮起。拆解不重画原视频；只有用户要求“用原子做出来”时才进入 [生成与修改](workflow.md)。

## 先取得动态证据

- 使用用户的视频文件，或通过宿主支持的方式实际打开视频链接。记下文件／链接、时长、画幅、源帧率和实际观看范围；未知项留空。网页标题、封面、字幕和作者介绍都不等于看过视频。
- 先正常速度播放目标段，再对快速动作、遮挡和切点慢放／逐帧。按动作补取入场前、中间、落定、退场及切点两侧的帧；均匀缩略图只用于定位，不能证明运动曲线或镜头连续性。仅有截图时只分析可见构图，无法确认的时间行为标为待验证。
- 时间码对应原视频；截取片段需保留偏移。可用宿主工具或 FFmpeg／ffprobe 抽帧和读元信息。变帧率视频按实际时间戳定位，不假设 30 fps；估计的时长、距离、曲线与参数要标注近似，未知帧率不用虚构帧号。
- 音画关系必须在实际听过后判断：指出动作对应的是节拍、重音、停顿还是乐句变化。无听音能力时写“未核验声音”，不从画面或音轨存在推断卡点。不能访问视频时说明具体阻碍与已看范围，请用户提供可访问的片段，不以反复换站代替观看。

## 按主体与时间拆，不按特效堆

先用一句话概括该段的视觉目的，再抓以下关系；只记录对该段有用的维度。

| 维度 | 观察重点 |
|---|---|
| 主体与层级 | 谁是焦点，文字／底板／徽记是否同组；谁遮住谁，是否有固定裁剪边界 |
| 动作 | 位置、尺度、旋转、透明度、颜色、形态；运动轨迹与枢轴；逐字／逐行／整体变化 |
| 节奏 | 预备、加速、减速、过冲、回弹、停稳、退场；多人或多个对象的延迟顺序；真正可阅读的停留时间 |
| 镜头与衔接 | 主体动还是镜头动；切点两侧的构图、方向、速度、大小与亮度如何接上；硬切、匹配剪辑、遮挡切换和叠化分别说明 |
| 质感 | 拖尾、运动模糊、辉光、色散、颗粒承担什么作用；它来自运动、材质、照明还是后期，只给有证据的判断 |

避免几种误判：全画面同向变化可能来自镜头或父组；文字越过固定边界后消失支持遮罩判断，而非单纯透明度；一张图放大不必然是三维推镜；透视、视差和自遮挡可作为线索，但不足以唯一还原原工程。看见发光并不能断言使用了辉光插件。区分持续变化与剪辑造成的跳变。

## 映射成可执行的动效语言

按「主体 → 属性 × 节奏 × 编排 ＋ 质感」提出最小可行组合，并解释每个原子的职责。到 [当前原子清单](../assets/catalog.md) 与 `atoms/<ID>.md` 核对真实 ID、`targets`、`writes` 和参数；需要时用 `node scripts/motion.mjs describe <ID>`。不要沿用参考作者的插件名或旧目录 ID。

- **直接可用**：原子支持该主体和行为。仍需按观察结果估计时间、位移、轴心和进出模式；这些是复现起点，不是测得的原作参数。
- **部分近似**：能复现某个运动层，但素材、遮罩或渲染需宿主配合。例如照片滑入可以复用 `prop.move` 的位移输出，图片绘制和裁剪由宿主完成，不能写进二维 MotionSpec 的 path 节点。
- **宿主另做**：真实三维镜头、材质灯光、骨骼、流体、视频合成和音频驱动等没有对应原子时，如实说明。硬切也无需硬配一个转场原子。

组合还需核对属性冲突、共享枢轴、前后绘制顺序、遮罩以及动作的接力。高置信度的视觉观察不等于高置信度的实现推断；不要把看起来相似说成底层实现相同。

## 交付能用于下一步的拆解

开头交代来源、已看范围与声音是否核验。主体用紧凑时间轴；关键行附时间码或抽帧证据，内容相同时可合并重复区段：

| 源时间段／证据 | 主体与可见变化 | 节奏、层级、接镜关系 | 候选原子与职责 | 支持程度／不确定处 |
|---|---|---|---|---|

实现建议与观察分开写。需要复现时，再补具体的起止状态、持续时间／错峰、落定与退场、层级与裁剪、宿主负责部分；参数写单位，范围足够时不装作精确测量。根据视频内容总结少量最值得借鉴的设计方法，不做通用审美清单。

## 下方时间轴的轨道、动作块与配色

- **按动效类型／原子分轨，一条轨道可以放多个独立动作块。** 例如“位移”轨道依次容纳“标题入场”“卡片滑入”“光标移动”，不用为每个主体单独开一条轨道。
- 每个动作块在拆解数据中保留主体名称、起止时间和高亮状态；画面内只画色块，**块内不加文字**。相邻、重叠的块都不能合并成长条；重叠时在该轨道内错层排列，避免暗块盖住亮块，块之间保留可见边界。
- **时间轴采用连续的平面轨道**：用轻微的交替底色、轨内留白和左侧短色标区分原子；整轨不加圆角容器、描边或卡片间隙，也避免高对比长横线。左侧保留各原子的名称／符号，分隔不要抢过动效主体。
- 一个块只对应一次连续动作，生效时整块提亮，其他块保持自己的状态。不要把整个轨道画成一条长条再只亮其中一部分，也不要把静止保持状态算进动作时长。优先保持轨道数量精简，复杂片段再按有意义的动作阶段分段。

- **不同原子必须使用不同颜色**，包括同一族中的不同原子；同一原子的不同动作块保留同色，名称仅保存在拆解数据和表格中，不能把所有生效块统一画成一种高亮色。
- 左侧轨道名称／符号与轨内色块保持同色系；同一原子在同一次分析的不同片段中保持颜色一致，不随行号或播放状态换色。
- 生效时提亮该轨道自己的颜色，未生效时降低同色的亮度或透明度。左侧轨道文字和色块都须与底色有足够对比，保留左侧名称、分组边界与时段标识，不能只靠颜色辨认轨道。
- 无论使用包内 CLI 还是宿主工具，最终动图都要符合这些要求。检查编码后的 GIF，确认调色板量化后各轨颜色仍能区分，标签与时间条仍然对应。

## 做拆解动图

固定顺序：**取得原片 → 通看并按节奏分段 → 每段写拆解文件 → 每段出一张动图 → 直接发出全部动图和总览**。

1. **取得原片。** 按来源分三种情况：
   - **用户直接给了视频文件**：直接用这个文件开始分析，不再找别的来源。
   - **只给了链接**：先把视频下载到工作目录（取不需要登录的最高清晰度，只要画面流即可），下载成功后用文件分析。遵守宿主对下载的确认规则；不绕过登录、付费或加密。
   - **链接下载不下来**：改为在网站上看。用宿主的浏览器打开原页面播放，暂停、逐帧跳到各时间点截图来分析，时间码取播放器的时间。这种情况拿不到原片片段，**不出拆解动图**，交付改为分段拆解表加每段的关键帧截图（入场前、中途、落定、切点两侧），并说明是哪一步取不到文件；用户之后给了文件，再补出动图。任何情况都不用重画原片来代替。
   时间码一律对应原片。
2. **通看并按节奏分段。** 先完整看一遍（全片按 1–1.5 秒抽帧定位），再按节奏切段：镜头切换、段落或风格切换、音乐乐句与重拍的变化（核验过声音时）、一组动作的起止。不按固定时长机械切。每段讲一件事：一个转场、一次入场、一组编排或一个段落的主体动作，通常 2–6 秒，最长 30 秒。重复的结构（每段都用的同一种转场）只拆一次，在总览里注明出现在哪些时间。用户指定了范围就只拆那一段。
   - 每一段再逐帧（至少每 0.1 秒）找出每个动作的起止、转折、颜色变化和切点。
3. **写拆解文件。** 时段用原片秒数。`tracks` 中每项记录一个具名动作块，用 `atom` 标明动效类型、`name` 标明主体与动作、`spans` 写该动作的时段。显示时按 `atom` 归入同一轨道；重复出现的动作仍是独立块，不合并时段：

```json
{
  "title": "风格切换转场 · 00:13.9–00:17.5",
  "source": { "video": "source.mp4", "from": 13.9, "to": 17.5 },
  "tracks": [
    { "atom": "prop.scale", "name": "外壳·第一次展开", "spans": [[14.2, 14.4]] },
    { "atom": "prop.scale", "name": "外壳·第二次展开", "spans": [[14.97, 15.17]] },
    { "atom": "timing.overshoot", "name": "外壳·第二次展开过冲", "spans": [[14.97, 15.17]] }
  ]
}
```

   每段一个拆解文件，命名带序号和内容，如 `03-shell-transition.breakdown.json`。`source.video` 相对拆解文件；整段不超过 30 秒。原子 ID 必须来自 [原子清单](../assets/catalog.md)；原片里没有对应原子的动作（三维镜头、材质、实拍）不写进轨道，写进拆解表的“宿主另做”。
4. **出图。**

```sh
node scripts/motion.mjs breakdown work/segment.breakdown.json --out work/segment.gif
```

   - 原片按时段截取、缩放到输出宽度（GIF 默认不超过 640 px，视频不超过 960 px），时间轴画在下面；除缩放和 GIF 调色板外不改动原片画面，没有声音。
   - 格式由扩展名决定：`.gif`（默认 25 fps；GIF 帧间隔是整百分之一秒，只接受 10、20、25、50 fps）、`.mp4`、`.webm`。`--width`、`--fps`、`--title` 可改。
   - 返回值里 `verified` 是对编码结果的帧数、尺寸、时长的读回，`tracks` 是每条轨道的原片时段。需要本机 Chromium 系浏览器和 ffmpeg。
5. **对照检查。** 从**编码后的动图**抽帧（如 `ffmpeg -ss 0.95 -i x.gif -frames:v 1 f.png`），核对同类动效是否归在同轨、原子轨道之间是否清晰分隔、动作块内是否无文字、重叠时是否互不遮挡，以及各块的高亮和配色是否正确。名称在拆解数据中保留；画面、时段或配色不符就改绘制方式／拆解文件重出。
6. **交付。** 先给一张分段总览（序号、原片时段、这一段讲什么），再按顺序给每一段的动图和拆解表。把动图本身直接发给用户：宿主能发送或内嵌文件时，在回复里发出 GIF，让它在对话中直接显示；只给文件路径或“已保存到某处”不算交付。同时附拆解表（时间轴上每条轨道在表里有对应说明）和拆解文件。截取的原片只用于这份分析，不当作素材再发布。

`breakdown` 也能接受 MotionSpec 场景，画出用原子做出来的动作和它的时间轴，用于说明自己做的场景，不用于拆解别人的视频。

**示例写法（虚构，不是对用户视频的观察）：**“00:01.20–00:01.65，标题从左进入、越过终点后回落；左缘有固定裁剪。候选为 `prop.move` ＋ `timing.overshoot`，宿主提供裁剪。位移约为画幅宽度的 20%，动作约 0.45 秒；只看到一次回落，暂不认定多次弹簧振荡。”

复现只学习可复用的动作关系与节奏，不因能观看就假定可提取原作素材商用。需使用原素材时单独确认许可。开始制作前把拆解转换为当前宿主的场景或逐帧代码，再按 [时间与画面检查](quality.md) 对照同一时间段播放与关键帧，记录复现偏差；“分析了”不等于“已经实现”。
